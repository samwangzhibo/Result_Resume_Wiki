端侧 AI Native 范式设计（通用版）

本文为通用方法论整理，不含任何特定企业的内部信息、经营数据或未公开方案；文中架构与流程均为可复用的设计参考。

摘要

  • 判断：生码能力已被解决，瓶颈在需求、验证、发布等占生命周期 70%–80% 的非编码环节；没有历史包袱的公司，拥有一次性把范式做对的窗口。
  • 总纲：确定性骨架管可控，概率性节点管智能——Spec 契约、Verify 闭环、白名单、置信度分流四道围栏圈定 AI。三个范式就是这一条规则套在三个对象上：
范式 套用对象 确定性骨架（工程管） 概率性节点（AI 管） 用到的围栏
AICoding 研发过程 Spec、数据字典、Verify 门禁、合并/发布批准 生码、生测试、修复 Spec 契约 + Verify 闭环
全栈跨端 技术栈 原生壳、纯 TS 契约层、三道退路、需求准入 一份 Spec 多端生成、ArkTS 补缺口 Spec 契约 + 共用 Verify
AI Native 架构 运行时产品 主链路、权限、Catalog 白名单、隔离降级 Agent 理解、规划、结论生成 白名单 + 置信度分流 + 人审
  • 路线：前两道围栏是后两道的前提，所以三范式按 AICoding 先行半步 → 跨端 P2 主战 → AI Native 架构 P3 主导 的顺序推进，三线共用一个试验田；存量走绞杀者双轨，默认渐进、重写不封死。
  • 节奏与收益：5–6 人小队，三阶段 12 个月；P1 可能比以前慢，P2 显现，P3 复利。北极星：需求上线周期 -40%~-50%、同等人力年迭代次数 ×1.6~×2、鸿蒙与主端同频；AI 主导的产品需求 P2 起落地样板，从"卖数据"走向"卖结论"。
  • 实施前的四个关键决策：小队规模、试验田、P1 度量口径、数据合规口径（见第 9 节）。

指标体系：北极星看结果、目标指标分到三条线、过程指标看健康。P1 的任务是把基线填上；◇ 为建议值，基线出来后校正。

范式 北极星指标（结果） 过程指标（健康度，P1 → P3）
AICoding 需求上线周期 -40% ~ -50%；同等人力年需求迭代次数 ×1.6 ~ ×2 需求代码率 30–50% → 70%+；单需求点人日 ◇ -40%；线下缺陷率 ◇ -30% ~ -50%；渗透率与完整采纳率分开记
全栈跨端 三端同频：鸿蒙与主端同版本上线，准入内需求 100%（并入上线周期） 一人三端需求数 1 → 2–3 → 准入内默认；三端总人日 / 单端人日 ≈3 → ◇ ≤1.5；架构漂移项趋零
AI Native AI 主导需求的业务收益：结论场景的转化 / 留存 / 交付时长（P2 样板出基线，P3 定目标） AI 主导需求数 2 → 新需求默认；结论采纳率涨、人审占比降；幻觉红线 0 漏网；单结论成本

◇ 为建议值，基线出来后校正；北极星按年看，过程指标进度量面板、不设单一 KPI。

1. 行业判断

结论：三股潮流已经跑通，但瓶颈全部从"生成"转移到"可控"；大厂方案太重，体量更小的公司的答案是用最小工程子集吃同一波红利。

  • AICoding：千问 3 个月周期 -50%、千行缺陷 -70%；快手鸿蒙生码 80%、2 人做三端——但渗透率 60% 时完整采纳仅 50%。
  • 全栈跨端：Flutter（闲鱼）与 KMP+Spec 双生成（快手）两条路线均已生产验证；RNOH 鸿蒙官方维护可用。
  • AI Native 端侧：A2UI 协议化（Google/腾讯/字节）、Jev 类概率投票模型成熟；残留问题是可信度、隔离降级与品牌风险。

2. 典型团队的现状与窗口

结论：业务有 Agent 化空间、技术是跨端甜区、组织有放大器红利、"业务不停车"是硬约束——四个条件同时成立，只允许渐进路线。

  • 业务：C 端卖线索型数据、B 端卖数据服务；下一程是 Agent 把"查一下"变成"给我结论"——研发范式升级与产品形态升级是同一件事。
  • 技术：展示型为主、实时性低、逻辑不复杂，是跨端与 AI 闭环的双重甜区；鸿蒙与主端同频是既定硬约束，靠人力三写撑不住。
  • 组织：小团队 × 放大器，但混乱同样被放大——所有选择偏向可回滚、小步验证。
  • 约束：老系统要维护、迭代不能停、跑着换底座、还不能影响线上数据。四件事同时做，排除无条件 big-bang 重写作为默认起点。

3. 总纲：确定性骨架 × 概率性智能

核心划界：状态/权限/契约/口径/主链路归工程；生成/理解/诊断/对话归 AI；人定目标、口径、边界、验收、责任。

圈定概率性的四个手段：Spec 契约前置 · TDD/Verify 闭环 · 白名单 Catalog · 置信度分流＋人审。

三个范式互为前提，单独推任何一个都会撞墙：

  • 跨端 → 给 AI 收敛战场：AI 闭环可靠性与栈标准化程度正相关；统一的上下文域、Spec、验证是 AICoding 的前提。
  • 架构 → 为 AICoding 铺轨：单一职责、显式契约、逻辑/UI 分层直接决定生码渗透率和验证闭环率；坏味道模块里 AI 只会照抄坏模式。
  • AICoding → 让存量重构第一次可行：特征化测试生成、契约对照、模块重写的成本压低一个数量级后，绞杀者式迁移在小团队才有经济性。
  • 第二圈：用这套范式开发出的 App 本身是运行时 AI Native 的——服务端 Agent 驱动端侧受约束渲染，产品从"卖数据"走向"卖决策"。

人永不退出的三件事：目标与优先级、数据口径与契约、合并与上线批准。

4. 范式一 · AICoding 工程体系（P1 先行半步）

4.1 方案

结论：瓶颈在反馈不在生码；小循环"生码→编译→Verify→修复"跑通，效率才真正释放。人面向协议与知识库，不面向逐行代码。

  • ① SDD 默认流：Specify→Plan→Tasks→Implement→Converge；Spec 是人机共同的唯一事实源，每个 Task 进入小循环。
  • ② Agent 小循环：生码→编译→Verify→修复；验证失败带证据回到生码，通过则人看证据批准合并。
  • ③ Verify 分层：L0 门禁（P1）→ L1 纯 TS 单测 PC 秒跑（P1）→ L2 半白盒（P2）→ L3 Catalog 化 UI 走查（P2）→ L4 需求级验收（P3）；不建重型平台。
  • ④ 小循环靠什么活、受什么约束：知识资产（业务 Spec、数据字典、技术 spec、Code Docs）喂给生码；模型分流（强模型理解/规划、弱模型执行/修复、MCP 不绑供应商）承载循环；数据安全（上下文分级、核心区只读、全程审计）约束循环。
  • ⑤ 人的角色：写/审 Spec、定数据口径、派活、看 Verify 证据、批准合并与发布；不逐行写、不逐行读；合并、发布、资金代码三件事不交给 AI。在本栈上人的熟悉度高、不确定性低；跨栈时（5.1）熟悉度弱、不确定性更强，因此对这套体系的成熟度要求更高——这是 AICoding 必须先行半步的原因。
  • 实测佐证：高可测模块 AI 单测质量可超人均，坏味道模块 AI 只会照抄坏模式——先有架构约束后有 AI 单测红利；能有效验收 AI 代码的人仅 10%–20%；渗透率 60% 时完整采纳仅 50%，渗透率与采纳率必须分开记。

4.2 难点与应对

结论：生码和 Verify 已经相对标准化，真难点在业务知识库——它对不对没人能肉眼判断、长会话会污染它、代码变了它不会自己跟。三件事共用一套评测体系解决。

  • 知识库怎么证明是对的：从历史需求抽样建 Golden 任务集，定期重跑，按一次通过率、人工改动量、Verify 通过率分模块出分；知识库每次变更前后对比，掉分即回退。分数进度量面板，和渗透率、采纳率并列。
  • 长会话降质与上下文污染：一次塞 10 个 ticket 上下文就爆，干扰项越多注意力越散，任务拆多细、何时开新窗口目前没标准。用 Golden 任务集压测出自家边界值（多少任务、多长上下文开始掉分），再规则化：单任务上下文预算、超预算即新会话加摘要交接、拆解粒度按预算反推；注意力治理——只喂相关的 Spec 和数据字典片段，上下文分级。
  • 代码变了，知识库怎么跟着变：代码合了知识库没更新，下一次生成就是盲人摸象。做联动准入：代码与知识库变更走同一分支同一 PR，合并前起工作流，用更新后的知识库重跑本需求和相关 Golden 任务；Verify 全绿且评测不掉分才合，不过则代码和知识库一起打回。P2 起作为合并门禁。

5. 范式二 · 全栈跨端：一人三端（P2 主战）

5.1 方案

结论：一个人面向 AI Coding 体系做三端，不面向三套技术栈。人管需求、方案与 Loop 校验，AI 在同向的分栈知识库上多端生成，三端共用 Verify。

  • ① 人：一个人不必精通 iOS/Android/鸿蒙三套栈。面向需求、技术方案、架构现状与基线，不面向具体技术栈，边做边补。做的是写/审 Spec、派活、看 Verify 证据、查方案是否符合架构基线、批准合并；不手写三端代码、不逐行读 ArkTS。不要求全员学三栈——那个成本不可承受。
  • ② AI Coding 体系：§4 已建的 SDD 流程、AI 多端生成、Verify 闭环、评测与联动准入。人只和这一层打交道，这是一人三端成立的前提。人的角色和 4.1 相同，区别是跨栈时人对目标栈架构的熟悉度更弱、不确定性更强，所以这里对 §4 体系的成熟度要求比本栈更高——AICoding 先行半步、跨端 P2 才主战，顺序由此而来。
  • ③ 分栈知识库与架构现状：业务 Spec、企业数据字典、架构基线三端共用；各端技术 spec、组件清单、Code Docs、现状分栈维护。三份知识库必须同向（5.2），否则 AI 读到的是三种架构。
  • ④ 三端产出：原生为壳、RN 主战、逻辑层纯 TS 三端共享；鸿蒙走 RNOH，缺口由 AI 生成 ArkTS 补齐；三端共用 Verify，输出证据报告回到人做 Loop 校验。
  • 需求准入：PRD 清晰、逻辑内聚、UI 简单、单端 <5pd 才走一人三端；关系图谱、扫码、支付、推送、极端长列表为原生保留地。
  • 人守什么：选型与退路决策、架构基线的升级裁决。

5.2 难点与应对

结论：一人三端有两种"不会"——人不熟其他技术栈，这个 §4 的体系已经解决，不是难点；真难点是同一个需求在三端架构上天然分叉，分叉越厚 Loop 越慢，必须做同向治理。

  • 第一种：人不熟其他栈——不是难点。人面向 AI Coding 体系和架构基线工作，技术栈细节由分栈知识库供给 AI；人校验的是方案与 Verify 证据，不是逐行代码。前提是 §4 的知识库评测和联动准入跑通，否则人就在盲校。
  • 第二种：架构分叉——真难点。鸿蒙与 iOS/Android 各自演进，知识库变三份、组件/分层/复用粒度各不相同：AI 生成的方案三端不可预期，Verify 能做但跑得慢，人校验方案的理解成本越来越高——知识库最终是要人理解的。长此以往 Loop 里人的环节被拖慢，系统迭代速度劣化、技术债累积。鸿蒙是分叉最容易发生的地方：生态不成熟、能力缺口多，AI 生成的 ArkTS 如果不按同一架构落位，鸿蒙知识库会最先漂走。
  • 治理什么：组件化方式（有哪些组件）、分层边界（UI/逻辑/数据）、业务组件复用的维度与粒度、目录/命名/依赖方向、契约与数据口径——五项三端对齐，广义一致、不求代码一致，差异只允许出现在平台适配层。
  • 怎么治理：架构基线写进知识库，作为 AI 生成和人 Review 的共同依据（P1 立基线）；一致性检查进 L0 门禁，分层越界、依赖方向、目录落位自动查，AI 生成的鸿蒙代码必须按同一架构落位（P2 起）；每阶段一次漂移 Review，决定收敛还是升级基线，不允许差异静默累积。

6. 范式三 · AI Native 端侧架构（P1 最小骨架 · P3 主导）

6.1 方案

结论：AI Native 不是加一个聊天入口或一条 AI 旁路，而是 AI 能力长在业务每一层里、每个 AI 点自带确定性兜底；智能主体在云，端负责交互、呈现、采集与兜底。

AI 主导的产品需求与收益——架构是手段，目的只有一个：让业务跑得更快。重构之后需求应该是 AI 主导的，它靠一个数据飞轮越转越快：

  • ① AI 主导的需求上线：Agent 给结论、端上受约束渲染，结论带来源、时间戳、置信度。P2 先上两个样板——尽调结论、风险研判推送。
  • ② 用户使用产生证据级数据：采纳、纠错、点开证据、追问，按"结论 ID × 来源 ID × 用户动作"采集；B 端纠错直达专家，是最贵的数据。
  • ③ 数据进评测与训练：Golden Set 评测、专家标注 bad case、Jev 阈值校准、RAG 知识库更新、微调。P2 人工回流起步，P3 自动化。
  • ④ 模型与编排更好：意图更准、结论更可信、模板更贴，置信度分流里自动放行的占比上升，灰度放量；更多场景交给 AI 主导，P3 新需求默认 AI 原生——回到 ①。

和推荐算法一样，越用越准；以前的循环是"需求→开发→上线→看数→下个需求"，人驱动、月级，飞轮是数据驱动、天级，人只守红线。飞轮转起来的标志看三个数：结论采纳率在涨、人审占比在降、AI 主导需求数在涨。架构是让它能转的轨道，动态化（6.2.1）是让它转得快。

行业通用骨架（抽象版，五层，端云各做什么）：

典型团队的端侧架构长在这个骨架上，端侧展开、云侧抽象，右列是推荐选型与分期：

  • 呈现与交互：搜索框即对话入口；尽调报告、风险推送、企业详情直接出结论；组件库即 A2UI 白名单；关系图谱原生保留地。选型：RN 页面 + 组件注册表，P2 样板 → P3 全量。
  • Agent 运行：端做闸门、云做作者——端上 Jev 入口闸做意图分流，容器持有生命周期，降级契约保主链路，动作回流走白名单；云上做规划、MCP 工具编排、Jev 模板闸与出口闸。选型：Jev 小模型（端）+ 大模型（云），P1 工具注册 → P2 编排。
  • 模型服务：云为主；端侧运行时架构预留不提前投，第一个候选是 Jev 意图分类小模型，触发条件是涉密离线/成本/弱网，P3 前端上只做渲染与兜底。
  • 数据回路：端只采集不训练——证据级埋点复用现有埋点 SDK 加字段，反馈同时喂 Jev 阈值校准与 Golden Set；云上 P2 专家人工回流起步，P3 自动化。
  • 治理与基础：企业数据 SDK ＝ MCP 工具集 ＝ 组件取数源，同一口径；模型网关 SDK 流式/超时/配额/熔断；AI 路径与主链路隔离。P1 骨架。
  • P2 起按业务触发追加：多模态解析（B 端尽调 PDF/OCR/表格，优先级最高）、长程任务状态机、成本治理、五维评测、Prompt/Skill 版本管理。P1 骨架不含，按刚需排期。
  • 人的角色：面向协议与白名单，不面向模型内部。建设期定规则——Catalog 收哪些组件、schema 怎么定、数据口径、置信度阈值；运行期守闸门——B 端敏感结论人工签发、回流 bad case、灰度放量与回滚决策；永不交出——动不动骨架、白名单增删、结论对外口径与责任。

A2UI：让 Agent 编排 UI 的模板式工程——三个问题，三个解法

Agent 的结论是动态的，需要灵活组织界面，但不能让它自由画 UI。做法是把业务做成可编排的组件模板，Agent 只在模板里搭积木。现有"服务端编排 + 组件自解析"的透传体系就是底座，区别只有一个——编排者从可信的运营规则换成了会幻觉的大模型，所以要解决三个问题：

  • 问题 ① Agent 编出来的东西怎么长在业务页面里——让它自由画 UI 就是样式不一致、三端不一致、品牌风险、没法 Verify；贴 WebView 又成了旁路。解法：Catalog，给它一份业务组件清单（结论卡、风险标签、证据列表、企业简介，每个就是页面上一个区域），样式在组件内部锁死，Agent 只决定出现哪些、什么顺序、填什么内容；不给布局原子。这份清单和跨端的组件清单是同一份（5.2）。
  • 问题 ② 编排者会幻觉，怎么不污染业务、不炸主链路——它会编不存在的组件、填错字段、把注册资本"改"了、下发不该跳的链接。解法：围栏，进门先查组件在不在清单、字段对不对，不对整块不渲染、退回字段展示；确定性数据只传 ID 不传内容，组件自己从企业数据 SDK 取，幻觉碰不到真实字段；生命周期归容器、动作走白名单；Jev 在入口/模板/出口/动作四处把关。
  • 问题 ③ 协议和生态都没定，怎么分期不返工——A2UI spec 还在 0.9 → 1.0 变动，各端渲染器版本不齐（原生、Flutter 有官方实现，RN 只有社区版）。解法：分期，P1 用现有透传协议做传输、Catalog 先注册 3–5 个业务组件、结构照 A2UI 定但不绑版本；P2 有限模板选形、大模型填槽，样板页跑通流式与兜底、拿结论采纳率基线；P3 评估放开自由编排，接官方生态是平移不是重做。载体先动态后回落，见 6.2.1。
  • 人定什么：清单里收哪些组件、字段怎么定、置信度阈值、动作白名单范围——人定；Agent 怎么拼、模型怎么选——人不碰，人看的是证据和分流结果。

6.2 难点与应对

结论：两个真难点——AI 的快和工程栈的慢怎么平衡；老架构边跑边换怎么不出事。前者用动态化先行、分级回落，后者用绞杀者双轨。

6.2.1 怎么平衡 AI 的快与工程栈的慢

问题：AI 把生成成本压到接近零，Catalog、模板、阈值、意图集每周都在变，数据回路要靠多轮灰度才能收敛；而原生技术栈一次发版两到四周，一轮验证就是一个发版周期。AI 一天能出三版，工程栈一个月才能放一版——回路转不起来。那就全上动态化？疯狂动态化之后 Bridge 序列化、JS 线程、启动开销一起来，性能顶不住又怎么办？

解法：先动态化拿验证速度，稳定之后分级回落拿性能，两件事按一个能力的生命周期分阶段做，不是二选一。

  • 动态态：先拿验证速度：载体是 RN 页面、Catalog 组件、模板、阈值配置，热更加灰度分钟级到用户，目的是拿真实回流数据跑出边界和阈值。一次发版一轮三个月只能试六次，动态下发一天能试三次。RN 在这里只是动态态的载体：快速验证用它，性能顶不住就按下面的路径回落，它不是终态。
  • 动态态 ≠ 无约束：热更包同样走联动准入与 Verify，灰度可回滚、单次放量有上限；热更内容限于 Catalog、模板、配置、页面逻辑，不动骨架、不动支付与权限。
  • 稳定态：回落要有资格：连续 ≥3 个迭代无结构变更、Verify 覆盖完整且 Golden Set 通过、有量（调用频次到阈值）、有痛（性能指标测得到瓶颈而不是感觉慢）、回落后契约不变（JS 侧签名和 schema 不动）。不满足就留在动态态，不为"原生更快"回落。判定由人做，数据由可观测给，每阶段盘点一次，和漂移 Review 同节奏。
  • 下沉态：按层回落：热点逻辑 → JSI 直调去掉序列化 Bridge；高频事件 → Native 事件流不过 JS 线程；稳定组件 → 原生实现、Catalog 里换绑定；固化模板 → 预编译；稳定决策 → Jev 端侧小模型或规则；极端页面 → 原生保留地。回落后失去动态性，再改要走发版，所以只回落已经不会变的东西；契约不变意味着对 Agent 和 Spec 透明。下沉后需求又变，先回动态态改、验证稳定再回落一次，不在原生上直接试错。
  • 和三条线的关系：AICoding——动态态改动小、频次高，正是 Agent 小循环最擅长的粒度，回落是一次有契约对照的重构；跨端——RN 主战的理由是动态化而不是跨端本身，三道退路（混合路由、纯 TS、JSI 下沉）就是回落的三条通道，第一天内建；AI Native——Catalog、模板、阈值、Jev 都先在动态态收敛，端侧模型运行时是"稳定决策回落到端"的终点，所以 P3 才投。

6.2.2 老架构边跑边换，怎么不出事

问题：老系统要维护、迭代不能停、要跑着换底座、还不能影响线上数据——四件事同时做。无条件 big-bang 重写的线上风险不可承受；但不换底座，AI 能力就只能以旁路形式贴在老架构上，永远成不了 AI Native。老架构这边怎么办？

解法：绞杀者双轨——存量不停、增量先行、逐模块替换；默认渐进，重写不封死。

  • 存量轨：让老代码"可被 AI 安全修改"——先做特征化测试锁住现状行为，再补 Code Docs 和数据字典，让 AI 有上下文可用；不追生码率。
  • 增量轨：新模块天生 AI 原生，按 6.1 的骨架落位；与存量轨共用同一套 Spec、数据字典与 Verify。
  • 替换顺序：叶子模块先行、同契约对照、灰度可回滚；每替换一个模块都是一次退路演练。
  • 重写不是禁区：模块自身闭环、不影响其他业务时可独立重写；是否重写按重建成本与业务窗口评估清单决策，不按立场决策。

7. 组织阵型与路线图

结论：一个 5–6 人 Harness 小队承载三条线，AICoding 先行半步、跨端 P2 主战、架构 P1 最小骨架 P3 主导；三线共用同一个试验田。

小队构成（5–6 人）：技术负责人 1（三线裁决）· Harness 工程师 1（AICoding Owner）· 全栈工程师 3–4（跨端 Owner）· Spec/质量 1 可兼（契约/数据字典/度量）。

  • P1（0–3 月）：工具+规范+L0/L1+数据字典 v1+架构基线+Golden 任务集；1 个 RN 页 + 1 个存量模块特征化测试；退出标准——≥1 需求端到端走通、拿到自家基线。
  • P2（3–6 月）：路由壳+Catalog、一人三端 2–3 个需求、鸿蒙同节拍交付、A2UI 样板与故障注入演练；联动准入与一致性门禁上线；退出标准——跨端有稳定样本、AI 通道灰度健康。
  • P3（6–12 月）：新模块默认 AI 原生、存量绞杀零事故、退路真实切换演练 ≥1 次；专项消失，成为默认工作方式。
  • 试验田：付费产品营销页 / 风险列表筛选器 / B 端报告模板；不选关系图谱与付费链路。
  • 预期：P1 写 Spec、补测试、搭基座，可能比以前慢；用 P1 的确定性投入换 P2/P3 的结构性收益。

8. 风险与不做清单

结论：三个致命风险（线上事故、品牌损伤、数据合规）均有工程对策；七条"不做"是方案可信度的来源。各范式的核心难点与应对见 4.2 / 5.2 / 6.2，此处只列行业共性的坑。

三个致命风险的兜底：绞杀者+灰度回滚（线上）｜引用溯源+人审+白名单（品牌）｜分级通道+只读权限+审计（合规）。

  • AICoding：存量适配是红利后的真墙（先建数据字典/Code Docs）· 会验收的人仅一两成（Review 准入不授权）· Token 成本与个人技巧团队化（模型分流、两周一轮收敛）。
  • 全栈跨端：没有"对端同学"兜底（AI CR 做厚 + 准入硬卡）· RN 性能天花板（三道退路第一天就位）· 鸿蒙生态不成熟（缺口交 AI 双生成）· 一人三端无冗余（结对起步、共用 Verify）。
  • AI Native 架构：幻觉对吃品牌业务致命（无来源不出结论 + Golden Set 红线）· 数据飞轮易空转（专家人工回流起步）· 成本延迟与新故障源（System1/2 分流 + 隔离降级）· 训练合规与组织断层（默认隔离授权；共建小组先培养人）。

七条不做： 1. 不做未经评估的全系统重写（闭环模块可独立重构，系统级按清单评估）； 2. 不自研模型、不自研 Agent 平台； 3. 不建大厂级重型测试/稳定性平台，第三方 APM 先行； 4. 不同时维护两套跨端栈，Flutter/KMP 是条件触发项； 5. 不在刚需出现前提前上端侧智能，P3 前云侧为主； 6. 不把生码率当唯一 KPI； 7. 不追求 100% 跨端、100% 无人工。

三句收口：上下文质量 ＞ 模型强弱；退路架构 ＞ 框架选型；可信 ＞ 聪明。

9. 实施前的四个关键决策

结论：四个决策确定后 P1 即可启动；六项待确认影响选型细节，不影响启动。

  1. 小队规模：确定 5–6 人 Harness 小队；成员从既有团队抽调还是外部补充。
  2. 试验田：付费产品营销页 / 风险列表筛选器 / B 端报告模板三选一或二；对应产品/QA 的排期窗口。
  3. P1 度量口径与指标体系：明确三层指标（北极星 / 目标 / 过程）；P1 按退出标准评估（≥1 需求端到端走通、拿到全部基线），P1 期间是否暂缓按常规交付速度评估。
  4. 数据合规口径：代码与工程上下文能否经外部 SaaS 大模型、私有化边界——直接决定 P1 工具链与模型分流方案；相关方案需通过所在组织的合规评审。
